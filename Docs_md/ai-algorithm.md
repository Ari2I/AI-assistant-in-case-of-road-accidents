# Алгоритм работы агента ДТП (Версия 3.0)

## Общие принципы
1. **Гибкий ввод**: Пользователь может отвечать развернуто, заполняя сразу несколько информационных слотов. Агент должен извлекать все доступные данные из одного сообщения.
2. **Сквозной контекст**: Данные, полезные для следующего этапа (например, марка авто, обстоятельства), сохраняются в общем контексте сразу при получении, даже если текущий этап еще не завершен.
3. **Ранний выход (Stop Factors)**: Проверка критических факторов происходит после каждого сообщения. При выявлении стоп-фактора диалог немедленно завершается инструкцией вызвать ГИБДД.
4. **Минимизация вопросов**: Агент задает вопрос только по тем данным, которых не хватает. Если пользователь уже предоставил информацию заранее, вопрос пропускается.

---

## Этап 1: Сбор фактов и первичная оценка (Step 1)

**Цель**: Собрать минимальный набор фактов для определения возможности оформления Европротокола.

### Слоты данных (Приоритет заполнения):
1. `safety_measures` (Аварийная сигнализация, знак)
2. `victims` (Пострадавшие люди) -> **СТОП-ФАКТОР**
3. `participants_count` (Количество участников) -> **СТОП-ФАКТОР** (>2 или 1)
4. `osago_status` (Наличие ОСАГО у всех) -> **СТОП-ФАКТОР**
5. `disagreement` (Разногласия + наличие приложения)

### Логика работы:
1. **Старт**: Анализ первого сообщения пользователя. Извлечение любых доступных фактов в слоты.
2. **Проверка стоп-факторов**:
   - Если `victims == True` -> **ВЫХОД**: "Вызывайте 102 и 103".
   - Если `participants_count != 2` -> **ВЫХОД**: "Вызывайте 102".
   - Если `osago_status == False` -> **ВЫХОД**: "Вызывайте 102".
3. **Генерация вопроса**:
   - Если все слоты заполнены и стоп-факторов нет -> Переход на **Этап 2**.
   - Если есть пустые слоты -> Формирование **одного** уточняющего вопроса по первому пустому слоту (с учетом контекста).
4. **Цикл**: Повторять шаги 2-3 до заполнения всех слотов или срабатывания стоп-фактора.

## Этап 2: Заполнение Европротокола (Step 2)

**Цель**: Помощь пользователю в корректном заполнении полей бланка извещения о ДТП и сбор данных для генерации PDF.

**Входные данные**: Контекст из Этапа 1 (марки авто, обстоятельства и т.д.).

### Поля для заполнения:
1. `datetime` (Дата и время)
2. `location` (Место ДТП)
3. `participant_a` (Данные водителя А)
4. `participant_b` (Данные водителя Б)
5. `circumstances` (Обстоятельства: маневры, знаки)
6. `damage_description` (Описание повреждений)
7. `scheme` (Схема ДТП)
8. `signatures` (Подтверждение подписей)

### Логика работы:
1. **Инициализация**: Перенос известных данных из контекста Этапа 1 в соответствующие поля.
2. **Пошаговый сбор**:
   - Для каждого незаполненного поля генерируется:
     - **Краткая инструкция**: Как правильно заполнить это поле (примеры формулировок).
     - **Вопрос**: Запрос конкретных данных у пользователя.
   - Пользователь может прислать данные для нескольких полей сразу -> Агент обновляет все найденные поля.
3. **Валидация**: Проверка полноты данных (например, наличие схемы или описания повреждений).
4. **Финал**:
   - Когда все обязательные поля заполнены -> Формирование итогового JSON-объекта для бэкенда (генерация PDF).
   - Выдача пользователю итоговой инструкции ("Распечатайте/сохраните...").

## Сценарии завершения

| Сценарий | Условие | Действие агента |
| :--- | :--- | :--- |
| **Стоп-фактор** | Пострадавшие, >2 авто, нет ОСАГО | Инструкция вызвать ГИБДД (102/103). Конец диалога. |
| **Успех (Европротокол)** | Все факты собраны, поля заполнены | Выдача JSON/инструкции по оформлению. Конец диалога. |
| **Отказ** | Пользователь хочет прекратить | Вежливое завершение. |
